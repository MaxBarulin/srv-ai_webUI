# Что и в каком порядке уходит модели

Сборка контекста чата — самая запутанная часть приложения: к ней сходятся
специализации, база знаний, вложения, инструменты, расчёты и размышления.
Здесь описано, из чего складывается запрос к LLM и почему именно так.

Код: `app/routers/chat.py` (`send_message`, `_build_history`), `app/llm.py`
(`build_system_prompt`, `stream_chat`).

## Один запрос к модели

```
┌─ system ─────────────────────────────────────────────┐
│ system_prompt.txt                                    │  §4
│   + дата, время, имя пользователя                    │
│   + промпт специализации ИЛИ свой промпт чата        │  §15
│   + CALC_SYSTEM_HINT          (если включены расчёты)│  §17
│   + каталог методик           (если они есть)        │  §17
├─ история ────────────────────────────────────────────┤
│ user:      текст + восстановленный текст вложений    │  §16
│ assistant: текст ответа                              │
│            + трасса расчёта впереди текста           │  §17
│            + reasoning_content — ТОЛЬКО у последнего │  §4*
│ …                                                    │
├─ user (вставляется перед последним сообщением) ──────┤
│ контекст из базы знаний            (если включён RAG)│  §8
│ ⚠ именно user: system в середине списка шаблон рвёт  │
├─ user ───────────────────────────────────────────────┤
│ текущий вопрос (+ картинки в формате image_url)      │  §16
└──────────────────────────────────────────────────────┘

tools:                набор инструментов (заметки/календарь + расчёты)  §7 §17
chat_template_kwargs: enable_thinking=false ЛИБО preserve_thinking=true
```

`§4*` — требование «история без reasoning» изменено решением заказчика
04.08.2026, см. раздел «Размышления» ниже.

## Агентный цикл: что происходит дальше

Ответ модели может оказаться не текстом, а вызовом инструмента. Тогда цикл
идёт по кругу — до `MAX_TOOL_ITERATIONS = 6`:

```
круг 1:  … → assistant(размышление + вызов) → tool(результат)
круг 2:  … → assistant(размышление + вызов) → tool(результат)
круг 3:  … → assistant(текст ответа)                            ← выход
```

Каждый круг — это полная генерация 35B плюс ожидание в очереди, поэтому цикл
экономят: каталог методик лежит прямо в промпте (иначе понадобился бы отдельный
инструмент поиска и лишний круг), а расчёт требуется выполнять одним вызовом,
а не по действию на круг.

Промежуточные ответы ассистента уходят обратно **вместе со своим
размышлением** — «interleaved thinking», штатный режим Qwen3.6. Без него на
каждом круге модель обдумывает заново то, что решила на предыдущем.

### Если вызов не распознан

Модель не всегда отдаёт вызов структурно. Разбираются три письменные формы:

| форма | где встречается |
|---|---|
| `{"name": …, "arguments": …}` | старые сборки llama.cpp |
| `<tool_call>{"name": …}</tool_call>` | обычный Qwen3 |
| `<tool_call><function=имя><parameter=ключ>…` | диалект Qwen3-Coder |

Последняя — родная для Qwen3.6 (в vLLM и SGLang её включают флагом
`--tool-call-parser qwen3_coder`). Бывает, что модель выписывает вызов текстом
прямо **внутри размышления** — тогда сервер его не видит и ход умирает пустым.
На таком мёртвом ходу вызов достаётся из размышления, но только:

- при включённых инструментах;
- только читающие инструменты (`_READ_ONLY_TOOLS`).

Второе ограничение — против подлога: размышление пересказывает содержимое
заметок, а общую заметку пишет кто угодно, и строка `<tool_call>` в чужом
тексте не должна оборачиваться записью в чужой календарь.

## Размышления

Три разных механизма, которые легко перепутать:

| что | где | управление |
|---|---|---|
| показывать размышления пользователю | блок «Размышления» в чате | всегда |
| генерировать размышления | `enable_thinking` в запросе | тумблер в чате |
| возвращать размышления модели | `preserve_thinking` | `PRESERVE_THINKING` в `.env` |

Возврат работает на двух уровнях:

- **внутри хода** — размышление каждого круга уходит вместе с его вызовом;
- **между ходами** — размышление сохраняется только у **последнего** ответа,
  у предыдущих снимается.

Ограничение «только последний» существенно: размышления бывают по 20 тысяч
знаков. Замер на цепочке из четырёх кругов показывает, что рост выходит на
полку со второго хода — около 10,5 тысяч токенов, то есть 8% слота на 131k.

Выключенные размышления имеют приоритет: при `enable_thinking=false`
переносить нечего, и в шаблон уходит именно этот флаг.

## Два числа про расход контекста — не путать

В чате их видно одновременно, и они означают разное.

**Внизу экрана, «чат: 11 200 ток. · 9% контекста»** — объём самой переписки.
Считается как `prompt_tokens` **первого** круга последнего ответа плюс сам
ответ: системный промпт, схемы инструментов, вся история и вопрос. Это то,
сколько уйдёт модели в следующем запросе. Красным — от 70%.

**Под каждым ответом, «пик 12%»** — самый тяжёлый запрос этого ответа:
`prompt_tokens` **последнего** круга плюс его генерация. У ответа с
инструментами промежуточные круги раздувают промпт вызовами и результатами,
но в историю они не попадают — в следующем запросе их не будет.

Поэтому «пик» всегда ≥ «чат», и падение пика между ответами — это нормально,
а не ошибка счётчика. Оба числа измерены сервером (`usage`/`timings`
llama.cpp), не оценены по символам. Живая строка во время генерации
(«размышляет · ~1234 ток») — наоборот, оценка по объёму текста: точные
счётчики приходят только в конце.

## Что НЕ уходит модели

- размышления всех ходов, кроме последнего;
- содержание чужих личных заметок и событий — инструменты исполняются от имени
  пользователя, видимость та же, что в интерфейсе (`app/scoping.py`);
- сырые файлы вложений: PDF и документы превращаются в текст, картинки —
  в `image_url`;
- персональные данные, если включён фильтр ПДн (§14).

## Порядок вставки — почему такой

**Каталог методик в системном сообщении, а не инструментом.** Поиск методики
стоил бы отдельного круга через модель, то есть секунд ожидания.

**Контекст базы знаний перед последним сообщением, и ролью `user`.** Так он
относится к текущему вопросу, а не ко всему разговору. Роль обязательно
`user`: шаблон Qwen3.6 сводит в системный блок только ПЕРВЫЕ одно-два
сообщения списка, а все остальные с ролью `system` молча выбрасывает —

```jinja
{%- if loop.index0 >= num_sys and message.role != "system" … %}
```

— поэтому системное сообщение в середине списка до модели не доходит вовсе.
На этом мы уже обожглись: контекст RAG вставлялся ролью `system` и терялся
целиком, хотя плашка «Источники» в интерфейсе показывалась. **Никогда не
кладите `system` никуда, кроме начала списка.**

**Трасса расчёта впереди текста ответа.** Как на экране: сначала посчитала,
потом сказала. Если бы шла после, модель на следующем ходу видела бы вывод
раньше обоснования.

**Пустые сообщения выбрасываются.** Иначе в историю попадали бы ходы, где
модель ничего не сказала, и шаблон получал бы пустой ход ассистента.

## Что происходит, когда ответа нет

Ход может закончиться без единого символа. Это редко, но случалось: по базе
восемь раз за три недели. Раньше пользователь видел пустоту, теперь —
объяснение, разное для трёх случаев:

- `finish_reason: length` — генерация оборвана по лимиту токенов;
- иначе — модель завершила ход, ничего не написав;
- в обоих случаях предлагается «Продолжить», и она работает: продолжение
  разрешено, если модель успела подумать или выполнить инструменты, и просит
  изложить ответ по уже собранным данным, а не считать заново.

## Как проверить шаблон, не гадая

Шаблон лежит в метаданных GGUF (`tokenizer.chat_template`) и отвечает на все
вопросы вида «а доедет ли это до модели». Достать и прогнать:

```bash
# что реально соберётся из наших сообщений
curl -s http://127.0.0.1:8000/apply-template \
  -H "Content-Type: application/json" \
  -d '{"messages": [...], "chat_template_kwargs": {"preserve_thinking": true}}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['prompt'])"
```

Что уже проверено этим способом:

- сообщение с ролью `system` в середине списка — **выбрасывается**;
- размышления внутри текущего хода рендерятся **без** `preserve_thinking`
  (условие `loop.index0 > ns.last_query_index`), флаг нужен только для
  прошлых ходов;
- с флагом у ответов без размышления появляется пустой блок
  `<think>\n\n</think>` — безвредно, тот же маркер, что и в режиме без
  размышлений;
- результаты инструментов рендерятся как сообщение `user` с обёрткой
  `<tool_response>`, и такие сообщения не считаются «вопросом пользователя»
  при вычислении границы хода;
- `arguments` вызова мы шлём **строкой** JSON (формат OpenAI, в нём их отдаёт
  и сама llama.cpp) — и это правильно, хотя шаблон разворачивает параметры
  только из объекта:

  ```jinja
  {%- if tool_call.arguments is mapping %}
  ```

  llama.cpp разбирает строку в объект сама, перед отрисовкой. Проверено
  сравнением `prompt_tokens` на одинаковых сообщениях: строка и объект дают
  одно и то же число (59 против 59 на сборке b8453). **Не «чините» это,
  подставляя объект** — прямой прогон шаблона мимо llama.cpp вводит в
  заблуждение, там параметры действительно теряются.
